## 1. Contexte et pourquoi

Le scan actuel (`surveiller_whales.py`) détecte les gros blocs **≥1000 BTC** et les
fragmentations **≥500 BTC**. Mais une baleine maligne peut déplacer des milliers de BTC
**sans jamais créer une seule transaction ≥1000 BTC**, grâce au mécanisme :

1. **Le Billet (UTXO)** : un UTXO est indivisible — pour déplacer une grosse somme, on
   dépense le billet entier et on reçoit le reste en « monnaie rendue » (change).
2. **Le Camouflage** : éclatement en un **arbre de milliers de micro-transactions de
   poussière (dust)** à frais quasi nuls, qui dorment invisibles au fond de la mempool.
3. **Le Déclencheur (CPFP — Child Pays For Parent)** : une transaction **« enfant »** à
   frais astronomiques, dépendant d'une sortie de l'arbre de poussière.
4. **L'Exécution** : le mineur est économiquement **obligé** de valider tout l'arbre parent
   (même à frais zéro) pour encaisser la prime de l'enfant. Le bloc se règle d'un coup.
5. **L'Expulsion** : le bloc massif expulse les transactions des petits porteurs.

**Les seuils publics (1000 BTC) sont connus des baleines — elles s'adaptent.** La réponse
n'est pas un seuil plus bas fixe (elles s'adapteront aussi), mais des **seuils statistiques
adaptatifs** (la ligne bouge chaque jour, elles ne peuvent pas s'y adapter) + les
**signatures inaltérables** (le frais astronomique de l'enfant EST le mécanisme).

## 4. LIVRABLE 1 — `Index_Maison/scripts/detecter_cpfp.py` (NOUVEAU)

Module v2, **mode silencieux par défaut** (`MODE = "observation"` — jamais d'alerte).

### 4.1 Les 3 cartes de détection

**Carte 1 — Z-score adaptatif (seuil qui bouge)**
- Base : moyenne mobile + écart-type des montants de gros blocs sur 7 jours glissants
  (lue depuis `whales_mouvements.jsonl` + `whales_scan_latest.json`).
- Déclenche : mouvement à **≥3σ** de cette moyenne, quel que soit le montant absolu.
- **Plancher absolu : ≥500 BTC** (filet de sécurité si la moyenne est trop basse).
- NOTE : cette carte s'applique AUX DONNÉES EXISTANTES du scan (elle ne modifie pas le
  scan, elle re-analyse ses sorties avec un seuil statistique).

**Carte 2 — Signature CPFP par frais (inaltérable)**
- Pré-filtre API (règle D7) : interroger mempool.space (`/api/v1/mempool`) UNIQUEMENT si
  on a déjà un signal local suspect, ou à cadence lente (1×/10 min), avec backoff + cache.
- Seuil v1 arbitré : transaction enfant avec **frais ≥20× la médiane** (des dernières
  heures, récupérée via l'API mempool) **ET** un parent direct à **≤1 sat/vB** **ET**
  **total de l'arbre ≥100 BTC**.
- Référence Cortana : ≥500 sat/vB pour l'enfant (à comparer pendant la calibration).

**Carte 3 — Accumulation de poussière (anticipation)**
- Mode passif : repérer dans `whales_mouvements.jsonl` les transactions à frais quasi
  nuls (<2 sat/vB) d'une même source sur 24-72h glissantes.
- Seuil v1 : **≥1000 adresses de poussière sur 48h** (référence Cortana : 4000 tx / 2h
  ou 10000 sorties / 6 blocs — à calibrer sur le réel).

### 4.2 Comportement (mode silencieux)
- Chaque run écrit dans `data/cpfp_detect.json` :
  - `ts`, `tip`, `zscores` (dernier z-score calculé par carte),
  - `cartes` : chaque carte avec `declenche` (bool), `score`, `detail` (texte),
  - `alerte_potentielle` (bool — MAIS JAMAIS émise en observation),
  - `confirmation` : nombre de runs successifs où la même signature apparaît (pour D6),
  - `calibration` : seuils observés (médiane frais, moyenne 7j, σ, max dust) — pour le
    bilan des 7 jours.
- **NE JAMAIS** écrire d'alerte vocale ni toucher live.json en mode observation.
- Écriture atomique, kill-switch, idempotent, stdlib uniquement, UTF-8, docstring.

### 4.3 Bilan de calibration (fin des 7 jours)
- `--bilan` : génère `Index_Maison/data/CPFP_BILAN_7JOURS.md` avec les seuils observés,
  le nombre de déclenchements par carte, les faux positifs estimés — **pour décision
  Christophe** (basculer en `MODE = "actif"` ou ajuster les seuils).
